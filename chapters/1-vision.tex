\section{Vision}
\label{sec:vision}

When it comes to data (and for that matter, any kind of data, not just multi-model), what we really want is to extract information from it---i.e., to ask questions about it and obtain answers---in a process commonly known as \term{querying}. In the context of multi-model data, this process naturally extends across the boundaries of different models and, in the case of polyglot persistence, across database systems as well.

Besides this primary goal, several additional milestones help us achieve it. We need to be able to \term{model} data so that we can reason about its structure and semantics---a necessary prerequisite for querying and for all of the capabilities described below. Sometimes, data is modeled first and created later. In other cases, we want to \term{infer} the schema from the data.

Both modeling and inference are closely related to the process of \term{evolution}. Whenever the schema changes, we have to propagate those changes to both the data and the queries that depend on it. In a multi-model data world, this might require us to \term{transform} the data between different models.

Lastly, our motivation concerns not only the correctness and completeness of multi-model data management, but also its efficiency. The primary functionality of a database system---querying data---should be as efficient as possible. Multi-model data offers additional opportunities to optimize querying by choosing the most appropriate combination of models for the task at hand. Doing so manually is very difficult, so we want the system to be able to adapt its internal data representation---in a process called \term{self-adaptation}---to the current workload and data characteristics.

\subsection{Level of Automation}
\label{sec:vision-automation}

Data management can be automated to various degrees. More automation is generally beneficial, as it reduces the amount of manual work and expertise required from users. It also allows the system to find solutions that might not be obvious to users or that would be too time-consuming to identify manually. Most importantly, an automated process can reduce manual effort and the risk of certain human errors.

The price of this is increased system complexity and potentially reduced control over the process. Therefore, we introduce automation gradually, following three distinct levels based on who the primary actor is~\citep{ideas2022vision}:
\begin{itemize}
    \item \term{User-driven} -- Users explicitly \emph{model} the data by creating a schema. They can create \emph{queries} over the schema and \emph{transform} the data between models. They can also \emph{evolve} the schema, and the system will propagate the changes to the data and queries.
    \item \term{Data-driven} -- The system automatically \emph{infers} the schema from the data. Whenever the structure of the data changes---either due to user actions or another process---the system \emph{infers} those changes and updates the schema accordingly.
    \item \term{System-driven} -- The system uses \emph{self-adaptation} techniques to proactively analyze the workload and data characteristics so that it can decide on its own to \emph{transform} the data into a new configuration of models that is most suitable for the current workload.
\end{itemize}

These levels are not strictly disjoint; they describe the dominant source of decisions and control.

\subsection{Challenges}

The main source of complexity in multi-model data management is the heterogeneity of the participating models. Each of them embodies its own unique, and often contradictory, assumptions about how data is structured, accessed, and queried. This makes it difficult to reason about the data as a whole and to design algorithms and systems that can operate across multiple models. In the \acrshort{nosql} world, this heterogeneity is further amplified by the lack of common standards and tools for managing data across different models~\citep{Jiaheng2023Survey}.

Some models (document, wide-column, key-value) are aggregate-oriented and naturally group related information into nested structures, while others (relational, graph, array) are aggregate-ignorant and prefer decomposition into flat records connected by foreign keys or references. Another important division is between schema-less models (document, key-value, wide-column), which allow flexible or only partially explicit structure, and schema-full models (relational), which require a fixed schema. This diversity is not limited to the data structures themselves. It also affects the associated query languages, integrity assumptions, and optimization techniques. Flat relational data and hierarchical \acrshort{json} documents call for different operators, just as table joins and graph traversals reflect different views of connectivity.

The theoretical data models have to be implemented in actual database systems, which adds another layer of complexity. Many \acrshort{nosql} systems are distributed by design, enabled by relaxed consistency and availability requirements (\acrshort{base}). This stands in stark contrast to traditional centralized relational systems, which are generally centralized and provide strong consistency guarantees (\acrshort{acid}). Differences in scalability mean that there is usually no \uv{one-size-fits-all} solution---the advantages of some databases or models become apparent only at certain scales, making any optimization approach even more dependent on the workload. On top of that, each database system has its own performance characteristics, leading to specific design decisions. For example, while normalization is a common practice in relational databases, document databases often prefer denormalization and redundancy to optimize read performance.

In fact, more than half of the 50 most popular database systems~\citep{DBEngines2026} are multi-model, i.e., they support multiple data models. Therefore, we have to consider not only different data models but also different combinations of models and their implementations across various database systems. The vast majority of these databases are not \emph{natively} multi-model, but rather started as single-model systems and later added support for other models. This means that multi-model support is often limited to a subset of the features of the additional models. Internally, the secondary models are typically implemented as interfaces to the primary model, which can lead to performance and consistency issues.

\subsection{Research Questions}
\label{sec:research-questions}

The vision described above is based on~\paperRef{vldb_2024} and captures the long-term goals of our research. Let us now refine it into concrete research questions. Some of them have already been addressed in previous work by our research group~\citep{mm_cat, mm_cat_journal, mm_quecat, koupil2023universal}:
\begin{itemize}
    \item \term{Modeling} -- How can heterogeneous data models be represented in a common semantic framework without erasing their model-specific structure?
    \item \term{Transformations} -- How can data be transformed between different models without the need to write custom transformation rules for each pair of models?
    \item \term{Querying} -- How can queries be unified across different data models, supporting a common, practically useful subset of features of each model, and allowing for cross-model queries and optimizations?
\end{itemize}
We use these answers as a foundation for the rest of our research. In this thesis, we address the following questions:
\begin{itemize}
    \item \term{Evolution} -- How can changes be propagated across conceptual and logical schemas, data, and queries in a multi-model environment? How can uncertain or ambiguous evolution decisions be supported by data-derived semantic evidence?
    \item \term{Self-adaptation} -- How can a multi-model system choose suitable representations for a workload without exhaustively materializing and benchmarking all alternatives?
    \item \term{Benchmarking} -- How can such systems be evaluated when real multi-model benchmarks and workloads are scarce?
    \item \term{Schema-free Query Unification} -- How can multi-model queries be unified when a shared conceptual schema is unavailable?
\end{itemize}
Many of these problems are common to single-model data management, but they are significantly more challenging in the multi-model world. In the following sections, we describe the specific challenges that we address, as well as our contributions to solving them.
