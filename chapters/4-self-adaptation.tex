\section{Self-adaptation}

With the categorical representation of multi-model data (see \Cref{sec:mm-cat}) and the capabilities of querying and evolution (\Cref{sec:querying,sec:evolution-propagation}), we have a solid foundation for managing multi-model data. Now we can focus on optimizing it.

In its most basic form, the problem we are trying to solve can be described as follows. We assume a fixed conceptual schema, a \term{workload} (a set of weighted queries), and a set of all available databases. Let us define \term{configuration} as a set of logical models of these databases that is capable of answering all queries in the workload. The goal is to find a configuration that minimizes the overall query latency. To define the problem more precisely, we derived the following open questions:

\question{sa:search-space}{Search space}{In general, there is inifinitely many configurations. We should find a deterministic way to limit the search space to a manageable size while still covering the best alternatives. Since even the number of \emph{meaningful}\footnote{I.e., configurations that are not redundant (up to renaming) or strictly worse than others.} configurations grows exponentially with the size of the conceptual schema, the alternatives must be generated systematically and efficiently.}
    
\question{sa:embedding-inlining}{Embedding, inlining}{Document model allows embedding related data together, which reduces the number of joins. Relational model allows inlining columns from one table to another. Evenso, some databases support embedding one model into another (e.g., PostgreSQL allows JSON columns in a relational table). The system should be able to identify opportunities for embedding and inlining, and to evaluate their benefits and costs. This includes not only the expected query performance improvement, but also the effort required to reach (and maintain) the new configuration.}

\question{sa:redundancy}{Redundancy}{Denormalization is a common technique for optimizing \acrshort{nosql} databases. It involves storing the same data in multiple places to avoid expensive joins. In a multi-model world, we can also consider redundancy across different models. Similarly to embedding and inlining, these techniques can significantly improve query performance, but they also introduce additional complexity and maintenance overhead.}

\question{sa:latency-estimation}{Latency estimation}{To evaluate a configuration, the system has to at least estimate the latency of the queries in the workload. A naive solution (executing the queries) is too  expensive. A much more efficient approach is required to make the search process feasible. Specifically, this solution cannot require actual materialization of the configuration, as that is, by itself, too expensive.}

\question{sa:cross-model}{Cross-model queries}{Given the nature of the multi-model environment, some queries may require data from multiple models. Therefore, the system has to be able to estimate latency of cross-model queries, taking into account the cost of data transfer and transformation between models.}

\question{sa:search-strategy}{Search strategy}{Even once a manageable search space is defined, the number of configurations grows too quickly for exhaustive evaluation. The system has to explore the space systematically, favor promising regions, and balance short-term exploitation with longer-term exploration.}

\question{sa:local-maxima}{Local maxima}{Cross-model queries are generally more expensive than single-model queries. Therefore, the search process may get stuck in local maxima, where any small change to the configuration would lead to an increase in latency. Only larger changes (e.g., moving a whole subgraph to another model) would lead to a significant improvement. The search strategy should be able to escape local maxima and find better configurations that are not reachable by small incremental changes.}

\question{sa:migration-cost}{Migration cost}{Migration to the final configuration is usually very expensive, as it may involve large data transfers and downtime. The performance gain of the new configuration must be significant enough to justify the migration cost. The system has to be able to estimate the cost of migrating to (and maintaining) a configuration.}
    
\question{sa:adaptation-timing}{Adaptation timing}{After a better configuration is identified and the cost of migration is estimated, it is still unclear when the adaptation should be executed. Immediate adaptation may react quickly to workload changes but incur excessive migration overhead, while delayed adaptation may miss important optimization opportunities. The system should therefore decide when the expected long-term benefit outweighs the large one-time migration cost.}

\question{sa:workload-prediction}{Workload prediction}{In practice, workloads are not static. They evolve over time and may contain periodic trends, bursts, or one-off anomalies. A truly autonomous system should reason not only about the present workload, but also about its likely future development, so that it can avoid overfitting to transient patterns and prepare for upcoming changes in advance.}

\question{sa:richer-state-space}{Richer search space}{Database applications offer a wide range of physical design choices beyond the logical model, such as indexes, materialized views, partitioning schemes, replication strategies, knob tuning, etc. These choices are not covered by the current categorical representation, but they can have a significant impact on query performance.}

\subsection{MM-mapsearch}

Based on the open questions above, we propose the following principles:

\begin{itemize}
    \item A \term{state} is a an element of a finite vector space that maps the conceptual schema and the databases to a configuration. \term{State space} is a graph of all possible states connected by available transitions.
    \item The state space is explored using an algorithm that evaluates the states both directly (by estimating the latency of the corresponding configurations) and indirectly (by the values of neighboring states).
    \item There is a model that, given a state and a workload, can cheaply estimate the total latency of the corresponding configuration without actually materializing it.
\end{itemize}

It is important to note that, while these principles are general and most likely applicable in other approaches to the problem of self-adaptation, they can be only enabled by a sufficiently robust representation of multi-model data.

In our approach, the categorical representation provides a unified view of the conceptual schema, the logical models, and the mappings between them. It allows us to describe queries (and thus the workload) independently of the actual configurations, as well as to reason about cross-model queries. It also defines a set of \acrshort{smo}s that offer a natural way to transform one configuration into another, which is crucial for defining the transitions between states. Lastly, we can use it to migrate the data to the final configuration.

An in-depth description and a proof-of-concept implementation of the proposed approach is provided in \paperRef{edbt_2026}. A short summary is provided in the following sections, together with a few improvements that we have made since the publication of that paper.

\subsubsection{State Space}

In our approach, we consider entities, not properties, to be the most basic building blocks. I.e., if an entity is mapped to a kind, all of its properties are mapped to the attributes of that kind. Then, a configuration tells us in which database(s) each kind is stored, and to which other kind (if any) is embedded\footnotei{Since we don't deal with the internal structure of the kinds, we do not distinguish between embedding and inlining, so we use the term \uv{embedding} for both.}{.} This limitation allows us to define a finite state space, as there is only a finite number of ways to assign the kinds to the available databases and to embed them into each other.

For example, consider the conceptual schema in \Cref{fig:schema_category}. It contains three entities: \object{User}, \object{Review}, and \object{Business}. Let us assume that we have three databases available: a relational database, a document database, and a graph database. We could define \term{state vector} as a vector of three elements, where each element corresponds to one entity and contains the database to which it is assigned. An \term{embedding vector} would also have three elements, where each element contains the entity into which the corresponding entity is embedded (or \code{none}).

This representation of state has one major issue---it does not allow redundancy, so if kinds used in a query are stored in multiple databases, the query has to be cross-model, resulting in a significant performance penalty. Such penalty is likely to outweight the benefits of using multiple databases, so the search process would lead to single-database configurations. To address this issue, we have replaced the previous two vectors with a \term{state matrix}. Its columns correspond to the entities, while its rows correspond to the databases. The values are on of:

\begin{itemize}
    \item \code{false}, if the entity is not stored in this database at all,
    \item \code{true}, if the entity is stored in this database, but not embedded into any other entity, and
    \item the identifier of another entity, if the entity is stored in this database and embedded into that other entity.
\end{itemize}

This allows us to represent both redundancy and embedding while keeping the state space finite. The number is possible states is further reduced by a handful of constraints, such as that an entity cannot be embedded into itself, or that all entities must be stored in at least one database. The resulting state space is still large, but it is manageable and can be explored systematically.

\subsubsection{Search Strategy}

Although the state space is finite, it is still too large for exhaustive evaluation. We have considered several search strategies, including greedy search, genetic algorithms, and integer linear programming. Finally, we have chosen \acrshort{mcts}, but we are still exporing other options.

The main idea behind \acrshort{mcts} is to incrementally build a tree of evaluated states. In each step, the algorithm first selects the most promising path from the root to a leaf node while balancing exploitation and exploration. Then, it expands the tree by applying a migration step to the selected leaf node, creating a new child node. A corresponding configuration is evaluated using the latency estimation model, and the result is backpropagated up the tree to update the values of the nodes along the path. 

A more detailed description of the algorithm can be found in \Cref{edbt_2026:sec:mcts}. The standard version of \acrshort{mcts} is designed for tree-structured search spaces (e.g., a game of chess), so we had to make some adjustments. For example, we use a \acrshort{dag} instead of a tree, as the same configuration can be reached by different sequences of migration steps.

\subsubsection{Latency Estimation}

Similarly to the search strategy, we treat latency estimation as a black-box function that can be implemented in various ways. So far, we have tried two approaches: a plan-structured neural network (see \Cref{edbt_2026:sec:neural-network}) and random decision tree.

Both approaches estimate the latency of a query from its query plan, which has to be obtained from the database. Although current databases still require the configuration to be materialized in order to obtain the query plan, there is no fundamental reason why this should be the case. Generally, databases generate query plans based on the schema and the statistics of the data. This information can be obtained once (e.g., from the database where the data is currently stored) and then used as an input to the planning engines of other databases.

Although this is still very much an open research question, we are optimistic that it can be solved in the near future, which would make the search process much more efficient. Until then, we can use the explicit materialization to train, test and validate the latency estimation models.\\

Once we can estimate the latency of queries in the individual databases, we can extend this estimation to cross-model queries by leveraging the query plans generated by the MMQL query engine. A simple cost model for MMQL queries was proposed and implemented in \Cref{strobl-mastersthesis}. It uses the estimated latencies of the individual subqueries, together with other metadata that can be obtained in a similar way (e.g., the size of the intermediate results), to estimate the overall latency of the cross-model queries.\\

Lastly, we can also use the latency estimation model to estimate both the cost of migrating to a new configuration and the cost of maintaining it. Our approach is to define a set of \code{INSERT}, \code{UPDATE}, and \code{DELETE} queries that represent the expected workload of the migration and maintenance processes, and then estimate their latency in the same way as for the workload queries.

However, this is still a work in progress, as there are many other factors that can affect the migration cost. For example, the cost of downtime does not depend only on the latency of the migration queries, but also on the \uv{business} cost of doing so, which, in turn, depends heavily on the specific application and its users. Nevertheless, the proposed cost model is a good starting point in the search for a more general solution to this problem, as it is able to provide all \uv{technical} information that is needed to estimate the migration cost, while leaving the \uv{business} part to the user.

\subsection{Index Optimization}

MM-mapsearch only optimizes the data layout on the logical level; it does not concern itself with the physical level. In \paperRef{dke_2026}, we conducted an in-depth study of indexes, which is a crucial aspect of physical level optimizations. We reviewed existing index-selection methods from relational systems and checked how they transfer to \acrshort{nosql} databases.

This line of work complements MM-mapsearch in an important way. While MM-mapsearch searches for a suitable \emph{configuration} in terms of logical models, mappings, embedding, and redundancy, index optimization shows that the logical design is only one part of the overall performance problem. Even after a promising configuration is chosen, its efficiency still depends on lower-level physical structures such as indexes. In this sense, \paperRef{dke_2026} primarily relates to \questionRef{sa:richer-state-space}: it shows that a truly self-adaptive system should eventually optimize not only where and how the data is represented, but also which physical access structures are maintained for the current workload.

At the same time, the paper confirms that the key technical obstacle is, once again, cost estimation. Existing index-selection methods rely heavily on the ability to estimate query costs for many alternative configurations without fully materializing them, which is precisely the same type of requirement as in \questionRef{sa:latency-estimation}. The difference is that here the alternatives vary on the physical level rather than on the level of logical models. This is encouraging for our overall approach---if we are able to estimate the latency of workload queries for candidate multi-model configurations, then the same principle can later be extended to physical-design choices as well.

Therefore, we do not view index optimization as a separate problem unrelated to MM-mapsearch, but rather as its natural continuation towards a richer adaptation space. The categorical representation gives us a principled handle on logical reorganization, whereas the index-selection work identifies what must be added for self-adaptation on the physical level. Together, these two directions suggest a broader long-term vision in which the system first reasons about model placement and structure, and then refines the chosen configuration using physical optimizations tailored to the observed workload.

\subsection{Contributions}

We formulated self-adaptation as a workload-aware optimization problem over the logical models and their mappings to a fixed conceptual schema. Instead of treating different data models resp. databases individually, our approach represents alternative configurations of the same conceptual schema in a common search space. This makes it possible to compare heterogeneous designs systematically and to reason about adaptation at the level of the whole multi-model system rather than one store at a time.

The categorical framework allowed us to define a state representation that captures the essential aspects of a configuration, including model assignment, embedding and inlining, (\questionRef{sa:embedding-inlining}), and redundancy (\questionRef{sa:redundancy}). This representation is both expressive enough to cover the most important design choices and compact enough to keep the search space finite (\questionRef{sa:search-space}). It also provides a principled way to migrate data between configurations.

On top of this representation, we introduced an automated optimization process that derives configuration changes from weighted workloads and explores them using \acrshort{mcts} (\questionRef{sa:search-strategy}). This algorithm enables us to systematically explore the search space, favor promising regions, and escape local maxima (\questionRef{sa:local-maxima}).

Because evaluating every configuration directly on the databases would be too expensive, we complement the search with learned performance estimation. In particular, we extend a plan-structured neural predictor~\citep{10.14778/3342263.3342646} for non-relational databases, so that configurations can be evaluated just from query plans of the workload queries, i.e., before they are materialized (\questionRef{sa:latency-estimation}). A similar approach is used to estimate cross-model queries (\questionRef{sa:cross-model}), as well as the cost of migrating to and maintaining a configuration (\questionRef{sa:migration-cost}).

Lastly, we implemented these ideas in a proof-of-concept prototype that integrates workload analysis, generation of schema variants, neural latency prediction, and an interactive interface for inspecting the recommended alternatives. Together, these results provide an initial practical foundation for automatic adaptation of multi-model data layouts under evolving workloads.
