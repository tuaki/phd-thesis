\chapter*{Commentary}
\addcontentsline{toc}{chapter}{Commentary}

Data management is a broad field that encompasses various aspects of handling data, such as modeling, storage, querying, and evolution. For years, the focus of data management research has been on relational data, which is structured in tables with fixed schemas~\citep{DBLP:persons/Codd71a}. In the early 2000s, the rise of \acrshort{nosql} databases~\citep{PolyglotPersistance} popularized new data models and formats, such as document, graph, key-value, and wide-column.

These models offer distinct advantages for certain types of applications and workloads, making them popular choices for handling unstructured, highly dynamic, or large-scale data (all of which are common characteristics of modern data). However, this diversity of data models comes with its own set of challenges. Moving data between databases that use different data models is much more complex and error-prone than migrating from one relational database to another. Generally, the \acrshort{nosql} world lacks unified theoretical foundations, common standards, and tools that would leverage them for managing data across various models~\citep{CSUR-Jiaheng}.

In real-world scenarios, these complex use cases involving multiple data models and databases are becoming increasingly common. Such data is often referred to as \term{multi-model data} (in contrast to the traditional approach of \term{single-model data}).

\begin{example}
\label{ex:mm-data}
The \emph{Yelp Academic Dataset}\footnote{\url{https://www.kaggle.com/datasets/yelp-dataset/yelp-dataset}} consists of \acrshort{json} collections representing \emph{businesses} (e.g., restaurants), \emph{users} (who write \emph{reviews} and tips about the \emph{businesses}), and the reviews and tips themselves. There is also a social network of \emph{friends}, as well as a set of \emph{checkins} and \emph{photos} associated with the businesses.

For the rest of this thesis, we will be using a subset of this dataset, displayed in \Cref{fig:mm-data}. Originally, the data is stored in a document model, but we transformed it into a multi-model representation. The \code{user} is a table in a relational model, the \code{business} is a collection in a document model, the \code{FRIEND} is a relationship in a graph model, and the \code{review} is a column family in a wide-column model. Crucially, the data from different models is connected via the same identifiers, allowing us to combine results from multiple queries.
\end{example}

The various data models from \Cref{ex:mm-data} illustrate the advantages of each model for different types of data. E.g., the relational model is suitable for structured data with fixed schemas, while the document model is better for semi-structured data with flexible schemas (e.g., many different options in the \code{attributes} field). The graph model excels at complex queries like finding the shortest path between two users in a social network, and the wide-column model is optimized for large throughput scenarios. On the other hand, this specialization comes with a cost---even though we can combine results from multiple queries, doing so is not straightforward, error-prone, and generally less efficient than querying a single model data.

The architectural decision to use a separate database for each model is called \term{polyglot persistence}~\citep{PolyglotPersistance}. It is a common approach in modern applications, as it allows developers to choose the best database for each part of the application not only based on the data model, but also on other factors such as scalability, consistency, and availability. \term{Polystores}~\citep{9252014} address some of the drawbacks of polyglot persistence by providing a unified interface for querying and managing data across multiple databases. However, they still have to deal with the heterogeneity of the underlying databases internally. Conversely, \term{multi-model databases}~\citep{SUR-Jiaheng} combine multiple data models into a single database application.

\subsubsection{Outline}

The rest of this chapter provides a high-level overview of the whole thesis; the next ten chapters, consisting of the individual papers, go into more detail.
\Cref{sec:vision} formulates the vision and research goals of our overall research (\paperRef{vldb_2024}), as well as the challenges of multi-model data management.
\Cref{sec:foundations} defines the common terminology and describes our previous work on modeling and querying of multi-model data.
\Cref{sec:evolution-management} proposes an approach to evolution management (\paperRef{cikm_2022}), which is then extended with propagation to queries (\paperRef{edbt_2024}) and the ability to choose between different propagation strategies (\paperRef{rcis_2025}). This is enabled by a novel take on functional dependency discovery (\paperRef{vldb_2025_fdephunter}).
\Cref{sec:self-adaptation} first reflects on our survey of index selection in heterogeneous database systems (\paperRef{dke_2026}) and then proposes an algorithm that allows the system to automatically choose a suitable multi-model configuration for a given workload (\paperRef{edbt_2026}).
\Cref{sec:related-concepts} discusses generating synthetic multi-model data and queries (\paperRef{enase_2025, edbt_2025}), which is crucial for benchmarking and testing the proposed approach. Then it goes beyond our approach by exploring a different way of multi-model data querying (\paperRef{vldb_2025_dortdb}).
Finally, \hyperref[chap:conclusion]{Conclusion} summarizes the contributions of this thesis and outlines future research directions.
