\section{Evolution Management}
\label{sec:evolution-management}

Everything is subject to change, and multi-model data is no exception. Changes can occur in any part of the system, such as the conceptual or logical schema, the data itself, or the queries. \term{Evolution management} involves detecting these changes, formally describing them, and propagating them to all affected components to maintain the system's consistency and correctness. The %last part, 
\term{change propagation} is especially challenging in a multi-model environment, where component relationships can be complex, and changes can have far-reaching consequences. Based on the related work (\Cref{sec:evolution-related-work}), we identified the following research challenges:

\defineQuestionPrefix{ep}{E}

\question{ep}{smos}{Model-agnostic evolution}{Changes in a multi-model system should be described and propagated in a way that is independent of the underlying data models, yet still precise enough to preserve consistency and correctness. Existing systems usually handle evolution separately for each supported model or for a narrow family of models. In contrast, a genuinely multi-model solution needs a shared conceptual view in which analogous changes can be treated uniformly despite differences in structure, constraints, and redundancy patterns across the participating models.}

\question{ep}{smo-intent}{Evolution language}{Given such a shared view, changes should be expressed in a formal language that can be understood by both users and the system. On the one hand, the language should provide a small set of well-defined atomic operations with explicit preconditions and postconditions, so that propagation remains analyzable and correct. On the other hand, users rarely think in such low-level steps, so the same language should also support higher-level operations that better capture restructuring intent while still being reducible to the atomic core.}

\question{ep}{data-propagation}{Propagation to data}{Once the schema of the data is changed, the data must be changed as well to maintain consistency. The most straightforward approach would be to load all data into some universal representation, apply the change, and then transform it back into the original model. However, this is not very efficient, especially for large datasets. Instead, we should be able to modify the data directly in the database via a sequence of \acrshort{ddl}/\acrshort{dml} statements---ideally, we would find the most efficient sequence of statements for the given change. Nevertheless, the completeness and correctness of the propagation are the most important qualities and should be guaranteed even if the chosen sequence is not optimal.}

\question{ep}{evolution-inference}{Change detection}{High variance and dynamicity are common characteristics of modern data. We should be able to detect changes in the data and keep the schemas up to date. Additionally, multi-model data naturally supports redundancy, both intra-model (i.e., some NoSQL databases promote denormalization) and inter-model (i.e., the same data can be represented in multiple models). Modifications to the data in one model (or part of it) should be reflected in the other models (or parts of them) to maintain consistency.}

\question{ep}{query-propagation}{Propagation to queries}{A dataset consists not only of data, but also of queries defined over the data. When the schema changes, queries must be updated to ensure they continue to return the intended results. This is particularly challenging in a multi-model environment where queries may span multiple data models and their relationships can be complex.}

\question{ep}{evolution-automation}{Evolution automation}{Some changes can be propagated automatically, while others require additional information (e.g., specific domain knowledge) to correctly interpret the user's intent. However, they should still be automated as much as possible. The user must be able to intervene at any point, but the system should decide when to explicitly prompt for user input and when to automatically select the optimal option.}

\question{ep}{migration-strategy}{Migration strategy}{There are multiple strategies for propagating changes to the data (e.g., \term{eager}, \term{lazy}~\citep{scherzinger2013managing}, and \term{hybrid}~\citep{scherzinger2016nosql}) and for reconstructing queries~\citep{DBLP:conf/er/CaruccioPT18, DBLP:conf/foiks/Ravve16, DBLP:journals/corr/abs-2403-09060}. The best strategy depends on the specific situation, such as the size of the data, the frequency of queries, the expected performance impact, etc. The system should support multiple strategies to accommodate a wide range of use cases, and it should also be able to choose the most appropriate strategy based on the current workload and data characteristics.}

\subsection{Evolution Hierarchy}

A change in one component that is propagated to another component is also a change, so it may require further propagation, leading to a cascade of changes that can be difficult to manage. This is especially true in a multi-model data world, where there are many different components and relationships between them.

Our approach starts by defining a clear hierarchy of components and a set of rules for propagating changes between them. At the top of the hierarchy (see \Cref{fig:evolution-hierarchy}) is the conceptual schema. The schema can be edited via atomic \emph{schema modification operations} (\acrshort{smo}s), which are either provided directly by the user or automatically inferred from data changes (as discussed in \Cref{sec:vision-automation}).

Next, the logical schemas can also be edited via \acrshort{smo}s (different from those used for the conceptual schema), which are automatically generated by propagating changes from the conceptual schema. The operations can also be created directly---either by the same use cases as the conceptual changes (i.e., user-specified or data-driven), or by the last use case from \Cref{sec:vision-automation} (i.e., self-adaptation).

Changes in the logical schemas are propagated to the data via \acrshort{ddl} and \acrshort{dml} statements. However, these changes do not affect \acrshort{mmql} queries, as they are defined over the conceptual schema and translated into native database queries only at execution time. Therefore, the queries are updated directly by the conceptual \acrshort{smo}s.
%\\

This top-down approach (i.e., from the most abstract components to the most concrete ones) is not the only way to propagate changes. A bottom-up approach is also possible---either originating from the data or from the queries. 
%
The former is achieved by observing changes in the data (e.g., a new field is added to a document collection) and inferring the corresponding \acrshort{smo}s that would have caused those changes. These \acrshort{smo}s are then applied to the conceptual and logical schemas, leading to the top-down propagation to the data and queries described above.
%
The latter concerns only changes in the query \emph{workload}, not in the \acrshort{mmql} query contents---the queries depend on the conceptual schema, not the other way around. The system can observe shifts in the workload (i.e., the frequency of certain queries) and use that information to trigger self-adaptation, leading to further changes in the logical schemas and data.

\subsection{Change Propagation}
\label{sec:evolution-propagation}

The \acrshort{smo}s were proposed in \paperRef{cikm_2022} and formally defined in \paperRef{rcis_2025}. For clarity, we divide them into three groups based on the level of abstraction:
\begin{itemize}
    \item \term{basic} -- atomic operations that work with individual objects and morphisms, e.g., \code{create}, \code{delete}, and \code{move},
    \item \term{composite} -- operations that work with frequent higher-level patterns, such as properties, relationships, arrays, sets, or maps (e.g., \code{createProperty} or \code{deleteMap}),
    \item \term{complex} -- operations that capture larger restructurings of existing schema fragments that involve coordinating several intermediate choices, e.g., \code{group}, \code{join}, or \code{asMap}.
\end{itemize}
This division is important for propagation---users can work with expressive high-level commands, but the system can still reduce them to a sequence of basic operations with explicit preconditions and postconditions. High-level operations capture the user's intent in greater detail, allow for more powerful optimizations (a complex operation can usually be decomposed into several ways, some of which are more efficient than others), and also offer better error handling (if one atomic operation fails, we can roll back the whole complex operation instead of having to deal with a partially applied change).

Once the change is expressed in this form, the system propagates it along the hierarchy described above. In \paperRef{cikm_2022, rcis_2025}, we further distinguish between two types of operations:
\begin{itemize}
    \item \term{light} -- the conceptual schema and mappings are updated, and the logical schemas and data remain unchanged,
    \item \term{heavy} -- the logical schemas and data are updated as well.
\end{itemize}
This distinction is useful because not every conceptual change must immediately trigger a full data migration---some operations can remain as logical adjustments until a heavier form of propagation is required.

Toward queries, we build on the approach from \paperRef{edbt_2024}, where schema changes are reflected in \acrshort{mmql}. More specifically, each query is analyzed through its selection and projection categories, which capture the graph patterns and returned structure over the conceptual schema. The propagation then evaluates how a given basic \acrshort{smo} affects these categories and related clauses such as \code{FILTER}, \code{DISTINCT}, \code{ORDER BY}, or aggregations. As a result, some changes have no observable effect, some lead to a restricted rewrite with potentially changed semantics or performance, and some are too destructive to be repaired automatically. In the last case, the system must either ask for additional guidance or switch to a different propagation strategy.

\begin{example}
\label{ex:evolution-add}
Starting with the conceptual schema and the wide-column logical schema (see \Cref{fig:mapping}), users may realize they want to be able to delete reviews. To do that, they use the \code{createProperty} operation to add a property \object{deletedAt} to the complex type \object{Review} in the conceptual schema and connect them via a new morphism (\signature{18}). This triggers the creation of the corresponding attribute in the logical schema via the \code{updateMapping} operation and the addition of the attribute to the data via the corresponding \acrshort{ddl} statements (\Cref{fig:evolution-add}).

Although \object{Review} is used in the \acrshort{mmql} query from \Cref{fig:query-multi}, the change is not propagated to the query because adding a property does not affect the query results. However, users might decide to add the property to the query manually to filter out deleted reviews (\Cref{fig:query-propagation-multi}).
\end{example}

\begin{example}
\label{ex:evolution-map}
A more complex use case is displayed in \Cref{fig:evolution-map}. The properties of the \object{Attributes} complex type represent various characteristics of businesses. In such a dynamic environment, it is common for new attributes to be added to the data. To do so quickly, users might convert \object{Attributes} into a key-value map using the \code{asMap} operation. The \object{Attribute}, \object{key}, and \object{value} objects are created, together with morphisms \signature{19}, \signature{20}, and \signature{21}. Note that morphism \signature{19} has the opposite direction from the previous morphism \signature{11}. This is because in the original schema, there was a \code{*:1} relationship between \object{Business} and \object{Attributes}. Now, there is a \code{1:N} relationship between \object{Business} and \object{Attribute} (one business can have multiple attributes).

After that, the old \object{Attributes} complex type is deleted. The logical schema is updated accordingly. This time, the change affects the query shown in \Cref{fig:query-single}, because \object{Attributes} was used in it. The query is rewritten to use the new objects instead, and the previous attributes are replaced with explicit string literals that filter the \object{key} property (\Cref{fig:query-propagation-single}).
\end{example}

Because propagation is defined over atomic operations, we do not have to execute the entire change in a single step. Composite and complex operations can be decomposed, analyzed, and then propagated incrementally, allowing the process to interleave with additional user input whenever an intermediate choice requires domain knowledge. The same decomposition is useful for scheduling---individual propagation steps can be postponed to a more suitable moment (e.g., when the system is underutilized) without losing track of the overall intent of the change. Regarding the data itself, our current implementation assumes eager migration, i.e., all affected records are updated immediately. Nevertheless, the framework is not tied to this choice. In principle, it can also support lazy or hybrid strategies by maintaining access to older versions of the conceptual schema, logical schemas, and queries until the migration is completed.

\subsection{Level of Automation}
\label{sec:evolution-automation}

As mentioned in \Cref{sec:vision-automation}, the process of change propagation can be automated to different degrees. Higher automation reduces the amount of manual work and expert intervention required from users, but it also places stronger demands on the metadata, propagation rules, and decision mechanisms available to the system. In our work, automation is therefore not treated as an all-or-nothing property. Instead, we distinguish three levels based on how much of the propagation process can be determined and executed by the system itself~\citep{ideas2022vision}.

\subsubsection{Rule-based Adaptation}

In the first level, the user or the change-detection mechanism specifies \emph{what} change should happen, while the system deterministically executes \emph{how} the change is propagated. This is the role of the \acrshort{smo}s and their propagation rules, illustrated by \Cref{ex:evolution-add,ex:evolution-map}.

The key property of this level is that the individual propagation steps are explicitly defined in advance. In \paperRef{edbt_2024}, we showed how this idea can be extended to queries---a change is decomposed into basic \acrshort{smo}s, the affected \acrshort{mmql} query is analyzed through its selection and projection categories, and the impact of each \acrshort{smo} on query constructs is evaluated. This allows the system to distinguish between changes that preserve query behavior, changes that require a restricted rewrite, and changes that are too destructive to synchronize automatically. While the first two cases can be handled systematically, the last one is reported back to the user as a point requiring additional guidance.

\subsubsection{Learning-based Adaptation}

This level builds on top of the previous one by retaining the deterministic propagation rules while allowing the system to decide \emph{which} admissible strategy to choose when several alternatives exist. In \paperRef{rcis_2025}, this problem appears mainly for information-capacity-decreasing changes, such as deleting a property used by existing queries. We investigated several synchronization strategies for such cases, in particular, phantom-based reconstruction and replacements based on functional dependencies or relaxed functional dependencies. Their selection depends on multiple criteria, such as whether the query can still be reconstructed, how much the new query increases in complexity, how expensive the required metadata is to maintain, and how faithfully the new query preserves the original results.

At this point, learning and heuristic decision-making become especially useful. The rule-based layer can enumerate admissible repairs, but it cannot, by itself, decide which trade-off is best for a given workload and system state. For example, a frequently executed query may justify a memory-intensive phantom representation, whereas a rarely executed query may be better served by a cheaper but less faithful rewrite based on functional dependencies. To make such decisions reliably, the system needs high-quality information about the structure of the data. In the case of query propagation, functional dependencies are especially important because they indicate which deleted values can be reconstructed from the remaining attributes and with what loss of precision.

This is the main motivation behind our new approach, which is designed not only to discover functional dependencies but also to distinguish between genuine, fake, and ghost functional dependencies. The approach, together with a proof-of-concept implementation called \term{FDepHunter}, is described in \paperRef{vldb_2025_fdephunter}.

Rather than treating dependency discovery as a fully automatic black-box task, FDepHunter provides an interactive workflow in which domain experts iteratively refine the discovered dependencies. Technically, it incrementally builds an Armstrong relation~\citep{DBLP:books/aw/AbiteboulHV95} enriched with positive and negative examples, which approximate the relevant properties of the complete dataset while allowing several questionable dependencies to be refined at once. FDepHunter provides a potential source of higher-quality semantic information in situations where purely automatic profiling would be too unreliable for downstream adaptation tasks.

\subsubsection{Self-adaptation}

The third level moves one step further---the system no longer only chooses how to propagate a given change, but can also decide that a change should be initiated in the first place. In this case, workload observations and performance estimates serve as triggers for structural modifications to the logical schemas and data layout. From the perspective of evolution management, this means that propagation is no longer merely reactive, but can become part of a broader optimization loop. Because this topic goes beyond the synchronization of already given changes, it is discussed separately in \Cref{sec:self-adaptation}.

\subsection{Related Work}
\label{sec:evolution-related-work}

Evolution management is challenging even in a single-model setting. Relational approaches typically benefit from a mature theory behind them, but they usually assume only one logical model and query language, as illustrated, for example, by the relational setting of~\citep{spivak2015relational}. \acrshort{nosql}-oriented work broadens the range of supported structures and migration strategies, but it is still usually tied to a single family of models or a single implementation platform. Moreover, most existing work focuses on schema evolution and data migration, while propagation to queries is often treated as a separate problem. In contrast, our approach integrates all these aspects into a single framework that can handle multiple models and their interactions.

Among the more relevant systems, \term{Darwin}~\citep{storl2022darwin} is important because it treats schema evolution as a practical migration problem rather than merely a modeling exercise. It supports lazy and hybrid migration strategies, as well as version jumps, unlike many other approaches that only support eager migration. However, its focus remains on aggregate-oriented \acrshort{nosql} stores and on propagation to stored data. It does not provide a model-agnostic conceptual layer in the sense used in this thesis, nor does it address query synchronization across a shared multi-model representation.

Another closely related approach is based on \term{U-Schema} and the \term{Orion} language, already introduced in \Cref{sec:foundations-related-work}. For the purposes of this chapter, the key point is that Orion provides a useful taxonomy of schema modifications across several models, but it remains centered on a unified representation at the logical level and does not integrate query propagation in the same sense as our \acrshort{mmql}-based approach. As a result, it does not treat evolution as one connected process spanning the conceptual and logical schemas, mappings, data, and queries.

This last point becomes particularly important once queries are considered. \term{Query rewriting}~\citep{10.1007/s00778-021-00676-3} usually aims at improving efficiency while preserving the query intent, whereas \term{query adaptation}~\citep{10.5555/1331939.1331940} reacts to changing runtime conditions and execution plans. Our problem is different---we need \emph{query synchronization}, i.e., adaptation of queries after schema evolution. Existing work in this area is much less common and usually remains single-model (especially relational~\citep{10.14778/1921071.1921078}), with only partial extensions toward \acrshort{nosql} databases~\citep{DBLP:conf/er/MollerKHS19} or polystores~\citep{9252014}. These approaches show that propagation to queries cannot be ignored, but they rarely combine it with model-agnostic schema evolution and direct propagation to data.

Overall, the existing literature is strong in isolated parts of the problem---some approaches focus on schema evolution, others on migration strategies, query rewriting, and workload-aware tuning. What is still largely missing is a unified treatment of evolution as propagation across a genuinely multi-model representation with explicit conceptual and logical schemas, mappings, data instances, and queries. Our approach builds on a shared categorical representation, supports all major model combinations through explicit mappings, and extends propagation not only to data but also to queries, including difficult cases with decreasing information capacity.

\subsection{Contributions}

\contribution{Unified Evolution Model}
We proposed a novel approach to evolution management in multi-model data management systems. It is based on a unified categorical representation of multi-model data, which allows us to include all supported data models and their combinations within a single framework. Thanks to the shared abstraction of logical models, we can express analogous modifications uniformly, rather than redefining them separately for each model, thereby improving both the expressiveness and the compactness of the overall operation set (\paperRef{rcis_2025}).

\contribution{Atomic Propagation Operations}
We defined a comprehensive set of atomic operations for modifying the conceptual and logical schemas, data, and queries (\questionRef{ep}{smos}). These operations can be propagated across all components of the system systematically (ensuring consistency and correctness) and with varying levels of automation (reducing the manual work and expertise required from users) (\questionRef{ep}{evolution-automation}).

\contribution{Higher-level Evolution Operations}
Besides atomic operations, we also defined more user-friendly composite and complex operations (\questionRef{ep}{smo-intent}), which are reduced to atomic operations during propagation. They can be used to express common changes in a more natural way while still being propagated through the system consistently.

\contribution{Query Synchronization}
Another contribution is the extension of our evolution-management approach to query synchronization (\questionRef{ep}{query-propagation}). When schema changes propagate through the system, the corresponding queries must also be adapted to preserve their intended results whenever possible. We focused especially on situations with decreasing information capacity, where some information may be removed or become unavailable after the change. For these cases, we investigated several rewriting and synchronization strategies in the multi-model context and showed how they fit into the broader evolution process.

\contribution{Prototype Validation}
Finally, we validated the proposed ideas with a proof-of-concept implementation of the tools MM-evocat (\paperRef{cikm_2022}) and MM-evoque (\paperRef{edbt_2024}). The implementation and experimental evaluation demonstrated that a substantial portion of the evolution process can be handled systematically, reducing manual, error-prone intervention when propagating changes across schemas, mappings, data, and queries. The experiments then compared the efficiency of the considered synchronization strategies and provided initial evidence of the approach's practical feasibility.

\contribution{Dependency-guided Adaptation}
Another, more focused contribution is FDepHunter (\paperRef{vldb_2025_fdephunter}), which strengthens the learning-based component of our approach by providing more accurate information about functional dependencies in real-world data. Although this is only a partial solution, it fits the broader evolution framework naturally---such dependencies provide exactly the kind of semantic insight needed for ambiguous query synchronization tasks and other situations where purely rule-based propagation is no longer sufficient. In this sense, FDepHunter is both a standalone tool for dependency discovery, and a supporting component that allows the system to make informed adaptation decisions.
