\section{Foundations}
\label{sec:foundations}

Our work is based on a preexisting approach to multi-model data modeling~\citep{mm_cat, mm_cat_journal} and querying~\citep{mm_quecat, koupil2023universal}. In this section, we introduce its main concepts and describe how it evolved into a comprehensive multi-model data management framework called \term{MM-cat}. We first clarify the terminology and the levels of abstraction used throughout the thesis. Next, we briefly introduce the categorical ideas on which the approach is built. We then show how the same conceptual representation supports both modeling and querying, which is the key reason why it later also serves as the basis for evolution management and self-adaptation.

\subsubsection{Common terminology}

% "Model" defines the language and structure of a data representation, while a "schema" is a specific instance of that model, describing how data is organized within that framework.

We distinguish three abstraction levels commonly used in database design: \term{conceptual}, \term{logical}, and \term{physical}. There is no universal agreement on the exact definition; in this thesis, we use the following interpretation. A conceptual schema is a \emph{platform-independent} description of the domain of interest. It captures business concepts and their relationships without committing to any particular database technology. Logical schemas are \emph{platform-specific} descriptions of how selected parts of the conceptual schema are represented in concrete data models. For example, a classical relational representation is flat, whereas a document representation can naturally express nesting. Moreover, particular database systems may further restrict or extend these schemas by their specific features. Finally, a physical schema describes the specific data structures used to store the data and implement indexes. In this thesis, we focus on the conceptual and logical levels, however we also discuss physical aspects when they are relevant to the overall approach.

These levels can be mapped to the terminology defined by \acrshort{mda}~\citep{MDA}---the conceptual level corresponds to the \acrshort{pim} while the other two levels correspond to the \acrshort{psm}. Nevertheless, we do not use the \acrshort{mda} in the rest of the thesis.

Each data model (or even each database system) has its own terminology for the concepts and data structures it uses. Let use define the following terms:
\begin{itemize}
    \item \term{kind} -- a class of items (e.g., a relational table, a collection of documents, or a collection of nodes/edges with the same label),
    \item \term{attribute} -- a field of a kind (e.g., a column in a table, a field in a document, or a property of a node/edge).
\end{itemize}
These terms unify the concepts from the logical level. On the physical level, we have:
\begin{itemize}
    \item \term{record} -- an item of a kind (e.g., a table row, a document, or a node/edge),
    \item \term{value} -- a value of an attribute in a record (e.g., a cell in a table row, a value of a field in a document, or a value of a property of a node/edge).
\end{itemize}
Finally, the terminology on the conceptual level is defined in a way that abstracts away any model-specific details:
\begin{itemize}
    \item \term{simple type} -- a value-carrying element (e.g., id, name, email),
    \item \term{complex type} -- a structure consisting of simple types (e.g., user, business, review),
    \item \term{projection} -- a directed connection between a complex type and another (simple or complex) type (e.g., a user has a name, a review is about a business),
    \item \term{properties} {[}of a complex type{]} -- a set of all simple types that are connected to the given complex type via a projection.
\end{itemize}

While kind has to correspond to a complex type, an attribute can correspond to either a complex type (e.g., a nested document in a document database) or a simple type (e.g., a column in a relational table). Relationships can be expressed in many different ways (e.g., references, embedding, etc.), so we do not define a unified term for them.

For illustration, let us show how these terms correspond to the classical \acrshort{er} model~\citep{ER} on the conceptual level:
\begin{itemize}
    \item complex type -- entity/relationship type,
    \item simple type -- attribute of an entity/relationship type,
    \item projection -- edge from an entity/relationship type to an attribute or another entity/relationship type.
\end{itemize}
The most significant difference is that we use complex types for both entity and relationship types because some data models (e.g., graph) treat relationships as first class citizens. Generally, we will not be using the \acrshort{er} terminology in the rest of the thesis.

\subsubsection{Category Theory}

Category theory gives us a compact language for describing structures together with the relationships between their parts. In this thesis, we use it as a modeling tool---it lets us describe data from different models in one common formalism while still keeping enough structure for querying, evolution, and transformations.

Let us start with a definition. A \term{small category} $\mathcal{C} = (\mathcal{O}, \mathcal{M}, \circ)$ consists of a set of \term{objects} $\mathcal{O}$, a set of \term{morphisms} $\mathcal{M}$, and a composition operation $\circ$ over morphisms. A morphism $f \in M$ is a directed connection between two objects $A, B \in O$, denoted as $f : A \to B$. For each object $A \in \mathcal{O}$, there is an \term{identity morphism} $1_A : A \to A$. Finally, the composition operation $\circ$ is associative and has the identity morphisms as its neutral elements.

In full generality, a \term{category} can have \emph{collections} of objects and morphisms (instead of \emph{sets}). In this thesis, however, we only work with small categories. For intuition, it is often helpful to picture such a category as a directed multigraph with objects as nodes and morphisms as edges. But we still have to keep in mind that a category is not given only by the nodes and edges; it also explicitly captures which paths can be composed and guarantees that composition behaves consistently.

In our setting, morphisms directly specified by the schema will be called \term{base morphisms}, while morphisms obtained by composition will be called \term{composite morphisms}. This distinction is practical rather than purely theoretical. Base morphisms capture the explicitly modeled projections, whereas composite morphisms let us refer to longer semantic paths through the schema.\\

A second key notion is a \term{functor}. A functor provides a structure-preserving mapping between categories. It is a function that maps all objects from the first category to objects in the second category (and similarly for morphisms), such that both identity morphisms and composition of morphisms are preserved.

The categories do not have to be the same size---for example, we can map multiple objects to a single object (and the morphisms between them to the identity morphism on that object). Or, we can map two objects connected by a base morphism to two objects connected by a composite morphism, which effectively expands the two objects into a more complex structure. In any case, the identity and composition preservation ensures that objects in both categories have the same \emph{semantics}.

\subsection{Modeling}
\label{sec:modeling}

The basic idea of our approach is to create a \emph{unified model} of multi-model data on both conceptual and logical levels, and to use it as the basis for all the operations on the data, including querying and evolution. This unified model is based on category theory, which allows us to capture the semantics of all existing data models in a consistent way.

The conceptual schema is a small category called \term{schema category}\footnotei{This definition of schema category slightly differs from the original~\citep{mm_cat, mm_cat_journal} which required that each morphism had a counterpart in the opposite direction (called \term{dual morphism}) and allowed each morphism to specify \term{cardinality} in the same way as an \acrshort{er} would (e.g., \code{0..*}). This is intentional, as the original definition was later refined (see \paperRef{cikm_2022}).

The current version does have the concept of dual morphisms, and the cardinalities are limited to \code{0..1} and \code{1..1} \emph{in the direction of the morphism}. For example, in \Cref{fig:schema-category}, we can immediately see that each instance of \object{User} can have at most one instance of \object{name} (even without providing any further information). This limitation is crucial to ensure that the conceptual schema can be mapped to any data model, because it requires each N:N projection to be decomposed to an intermediate complex type with two N:1 projections. A more fine-grained cardinality control is achieved via categorical concepts like \term{monomorphism} and \term{epimorphism}.}{.}
Its objects represent the concepts in the domain of interest---complex and simple types, while its morphisms represent projections between these concepts. An object represents a simple type if there is no morphism from it to any other object; otherwise, it represents a complex type.

\begin{example}
\label{ex:schema-category}
\Cref{fig:schema-category} shows a schema category that models the data from \Cref{fig:mm-data}. Categorical objects (representing complex and simple types) are displayed as ovals. Each object has an internal identifier (not shown in the figure for simplicity) and a label. By convention, complex types have their labels capitalized (e.g., \object{User}) while simple types have not (e.g., \object{id}).

Morphisms (representing projections between types) are displayed as arrows. For convenience, we identify each of them by a unique integer \term{signature}. E.g., morphism with signature \signature{1} corresponds to the projections between a complex type \object{Review} and its property \object{id}. Morphisms can also have human-readable labels, but they are not displayed in the figure for simplicity. Identity morphisms are omitted for the same reason, although they are present internally (they are required by the definition of a category).
\end{example}

On the logical level, each kind has its own logical schema. A logical schema is also a schema category, but it is defined over a specific data model. Therefore, its objects and morphisms have a very specific semantics; e.g., in a relational model, there would be a complex type representing the table, simple types representing its columns, and projections between them, meaning that the columns belong to the table. Because the underlying kinds are always trees (e.g., a row is just a tree with depth 1), the schema categories of logical schemas are also trees with a distinguished \term{root object}.

The logical schema category has to conform to the constraints of the underlying data model. For example, in a traditional relational model, columns cannot contain array values, so there cannot be a morphism from a \uv{column object} (i.e., object representing a column) to a table object. However, in a document model, there is no such restriction, so we can have a morphism from a field object to a document object, representing the fact that the field is an array nested inside the document. We can also rename objects in the logical schema to conform to the naming conventions of the underlying database system, or to avoid name clashes with attributes of different kinds.

Finally, each logical schema is connected to the conceptual schema via a \term{mapping}, which is a functor that maps objects and morphisms between both schema categories (from the logical to the conceptual). This allows us to preserve the semantics of the conceptual schema while still being able to use the specific features of the underlying data model.

\begin{example}
\label{ex:mapping}
Continuing \Cref{ex:schema-category}, \Cref{fig:mapping} displays a logical schema category for the wide-column database from \Cref{fig:mm-data} (in red), mapped to the conceptual schema category from \Cref{fig:schema-category}. The root object of the logical schema is \object{review}, which is mapped directly to the \object{Review} object in the conceptual schema.

Column family \object{review} cannot have a column \object{user}, because user is a complex type and wide-column model does not support nested structures. However, we can \term{embed} the \object{id} simple type into \object{review} by defining the object \object{user\_id} (mapped to the object \object{id} from the conceptual schema), and the morphism \signature{3.4} (mapped to the morphism from \object{Review} to \object{id} in the conceptual schema). The dot symbol represents a composite morphism---in this case, morphism \signature{3.4} corresponds to the composition of morphisms \signature{3} and \signature{4}.

Because a schema category of a logical schema is a always a tree, we can express both it and its mapping to the conceptual schema in a single \acrshort{json}-like structure. It shows the root object, its attributes, and the signatures of the morphisms to them (displayed on the right of the figure).
\end{example}

\subsection{Transformations}

In our approach, transformations are a direct consequence of modeling. We defined \term{instance category}~\citep{mm_cat, mm_cat_journal} to have the same structure as the schema category, but to also contain the actual data records. We also developed algorithms that leverage the above-mentioned mappings between the conceptual and logical schemas to transform data from a database to an instance category and back~\citep{mm_cat_journal}. This allows us to transform data between any two models by first transforming it to the instance category and then transforming it to the target model. The mappings ensure that the semantics of the data is preserved during this process.

The transformation algorithms are mostly database-independent, but they have a few database-specific parts, i.e., the concrete data structures and \acrshort{ddl} and \acrshort{dml} statements. Therefore, for each supported database, we have to define a \term{wrapper}, which implements all of the database-specific parts. The same approach is used in other places as well---for example, during querying (which will be explained later), the algorithms are database-independent; only the translation to the native query languages is database-specific and implemented in the wrapper. Evolution management also works in the same way. Crucially, the underlying algorithms are general enough to support \emph{all} major data models considered in this thesis; the wrappers handle only the technical details of each database.

\subsection{Querying}
\label{sec:querying}

Although most relational databases use the query language standard (\acrshort{sql}~\citep{SQL}), there are still many differences in the syntax and semantics of the language between different database systems. For example, some databases support specific features like window functions or recursive queries, while others do not. This can make it difficult to write queries that work across multiple databases, even if they all use \acrshort{sql}.

In the case of \acrshort{nosql} databases, the situation is even more complex. Each database system has its own query language, tailored to the specific data model. From \acrshort{sql} to XQuery~\citep{XQuery}, these languages have vast differences in both syntax and semantics. Even within the same data model, query languages (e.g., SPARQL~\citep{sparql} and Cypher~\citep{Cypher} for the graph model) offer very diverse features~\citep{Jiaheng2023Survey}.

There are attempts to unify query languages across different data models, most notably by extending \acrshort{sql} with additional features for specific data models. However, these extensions are often limited in scope and do not cover all possible queries across all data models. For example, SQL/JSON~\citep{SQLJSON} allows querying both relational and JSON data, but it does not support other data models like graph. Similarly, SQL/PGQ~\citep{SQLPGQ} allows querying property graphs, but it does not support documents.

Within a system based on polyglot persistence, querying multi-model data requires running multiple queries in different query languages and then manually combining their results, which is a complex and error-prone task. Moreover, mastering multiple query languages takes a lot of time and effort, and it is not realistic to expect users to be proficient in all of them. This is a huge barrier for using multi-model data efficiently. To address this issue, we want to be able to query multi-model data using a single, unified query language. Such a language should be expressive enough to cover all queries across all data models, and it should recognize all possible data structures that can be returned by these queries.

Lastly, one of the primary motivations for using multi-model data is the performance benefits from using the best model for the given job. Therefore, in order to fully realize these benefits, the overhead of using the unified query language should be minimal, ideally negligible compared to a native solution.

\subsubsection{MMQL}

These requirements led us to the development of \term{multi-model query language} (\term{\acrshort{mmql}})~\citep{mm_quecat, koupil2023universal}. \acrshort{mmql} is a query language over the schema category, making it independent of both the underlying data models and the specific databases. After parsing, the query engine splits the query into maximal subqueries that can be executed on a single database, translates them to the native query languages, executes them, and finally combines the results.

The syntax of \acrshort{mmql} is based on SPARQL~\citep{sparql}, as it is a well-known and widely used query language for graph data (and schema category can be represented as a multigraph). Each triple pattern in the query corresponds to a morphism in the schema category, together with its source and target objects. However, the similarity to SPARQL is just syntactic, as both objects and morphisms in the schema category can have very different semantics dependent on the underlying data models and databases. E.g., one morphism can represent a join in a relational database, a relationship kind in a property graph database, or a nested document in a document database.

A single \term{query plan} is created by matching the patterns in the query to the available logical schemas (via the mappings from the schema category). Because of redundancy, more than one combination might be possible. In that happens, multiple query plans are created and the best one is chosen based on the estimated cost.

\begin{example}
\label{ex:querying-single}
Going back to the schema category from \Cref{fig:schema-category}, we can query the following information: \emph{Find all businesses that allow dogs. For each business, return its name and whether it has TV available}. This process is displayed in \Cref{fig:query-single}.

First, we use the \code{WHERE} clause to express the pattern we want to match in the logical schemas. The names of the variables (prefixed with the \code{?} symbol) are arbitrary, as the triples are identified by the signatures of the morphisms. The \code{true} literal acts as an implicit filter. Next, the \code{SELECT} clause describes the structure of the result, which is an object with two fields---\code{name} and \code{hasTV}.

In the example, the \code{WHERE} pattern is matched to the logical schema of the document database (in this case, MongoDB), so the query engine translates it directly to the native query language. After executing the query, the results are projected to the structure defined in the \code{SELECT} clause and returned to the user.
\end{example}

Optimizing query plans is crucial to the performance of any database system. In our case, it is even more important, as we have to manage multiple databases simultaneously. We do not try to optimize the native queries themselves, as that is the responsibility of the underlying applications. Instead, we have explored, implemented, and evaluated several techniques to improve the performance of the \acrshort{mmql} query engine~\citep{strobl-mastersthesis}:
\begin{itemize}
    \item \term{Predicate pushdown} -- Generally, it is more efficient to filter the data as early as possible, ideally in the underlying databases, so we push the predicates down along the query plan tree. Not all operations can be pushed to the databases (e.g., cross-database joins), so they are executed in the query engine. In some cases, the databases do not support certain operations (e.g., aggregation), or they might not be very efficient (e.g., lookups in MongoDB), so we have to execute them by ourselves as well.
    \item \term{Dependent joins} -- If one side of a join depends on the results of the other side, we might be able to push this as a \uv{filter} to the database. E.g., when two kinds are joined on a key, we can query one of them first and then use the possible key values as a filter for the second one. This is especially beneficial when the first kind is already heavily filtered by other predicates. This is shown in \Cref{fig:query-multi}.
    \item \term{Cost estimation} -- The cost of plans and subplans is the most important factor for plan creation and selection. We have implemented cache-based cost estimation, allowing us to reuse the results of previous queries and to learn from them over time. We have also implemented a simple cost model based on the cost estimated by the databases and the number of records processed by each operation, which is used when there is no information in the cache.
\end{itemize}

\subsection{MM-cat framework}

\term{MM-cat} framework is an umbrella term for a family of tools based on the unified representation described in \Cref{sec:modeling}. They provide a proof-of-concept implementation that allows us to test the proposed approach, evaluate its feasibility, and demonstrate its capabilities.

\begin{itemize}
    \item \term{MM-cat}\footnote{The first tool has the same name as the entire framework.}~\citep{mm_cat} enables multi-model data modeling and data transformation across various models.
    \item \term{MM-evocat} (\paperRef{cikm_2022}) adds the ability to evolve conceptual schemas and propagate changes.
    \item \term{MM-infer}~\citep{mm_infer} (later extended in \paperRef{enase_2025, edbt_2025}) allows to infer conceptual and logical schemas from the data.
    \item \term{MM-quecat}~\citep{mm_quecat} enables querying multi-model data using \acrshort{mmql}.
    \item \term{MM-evoque} (\paperRef{edbt_2024}) allows propagating changes from conceptual schemas to queries.
    \item \term{MM-mapsearch} (\paperRef{edbt_2026}) explores the concept of self-adaptation.
\end{itemize}

The overall architecture of the system is shown in \Cref{fig:architecture}. There are three levels of abstraction (conceptual, logical, and physical), each with its own artifacts (schema categories, mappings, and data). The arrows show interactions between various parts of the system enabled by the tools. For example, MM-infer observes the data and infers both the conceptual and the logical schema categories. The MM-cat tool has two distinct components (\emph{modeling} and \emph{transformations}), which are displayed separately. The colors of the arrows do not have any particular meaning; they are just used to distinguish between different interactions. Although the tools roughly correspond to the capabilities described in \Cref{sec:vision}, in practice, they are more of different \emph{use cases} of one unified system than a set of separated tools.

\subsection{Related Work}
\label{sec:foundations-related-work}

Traditional conceptual modeling is, among others, based on \acrshort{er}~\citep{ER} or \acrshort{uml}~\citep{UML}. These formalisms remain important because they provide a technology-independent description of the domain, but they were not designed as a unifying framework for heterogeneous multi-model systems with explicit cross-model mappings, embedding, or redundancy. They are therefore useful mainly as inspiration for the conceptual level, not as a complete solution to the broader problem addressed in this thesis.

Besides these classical approaches, several proposals target multi-model data more directly. Probably the closest practical line is represented by \term{U-schema}~\citep{DBLP:journals/is/CandelRM22} and its extensions, such as the \term{Orion} language~\citep{DBLP:conf/er/ChillonRM21a, 10.1109/TKDE.2024.3362273} for evolution and \term{SkiQL}~\citep{skiql} for schema querying. Their main difference from our framework is the chosen level of unification. U-schema primarily unifies data models on the \emph{logical}, rather than the \emph{conceptual}, level. This leads either to an inability to tailor the representation to the specific features of each data model (if we use one logical schema for multiple databases), or to a redundancy and a loss of semantics (if we use multiple disconnected logical schemas). Our approach keeps a platform-independent conceptual schema and connects it to specialized logical representations through explicit mappings. This separation gives us more freedom to tailor each logical schema to the capabilities of a concrete database system while still preserving one shared conceptual view. 

A second difference is in the querying capabilities. SkiQL is a \emph{schema} query language, meaning it can only query the structure of the data, not its content. This is a very important distinction, as our focus is on the opposite---we only query the contents of the data, not its structure. However, this is not a limitation of our approach, as we can still get the structure either from our internal model or from the data (i.e., by inference).

There is also a more theoretical category-theoretic approach to heterogeneous data management~\citep{DBLP:journals/corr/abs-2201-04905}. A recently published version~\citep{lu2025part1, lu2025part2} is much more rigorous and comprehensive while also exploring querying multi-model data. It introduces categorical algebra and calculus as an extension of relational algebra and calculus via multi-model predicates. These works provide valuable formal foundations for representing multiple models and reasoning about transformations between them. Compared with our work, however, they focus more on the formal apparatus itself than on an integrated toolset for modeling, querying, schema inference, and evolution over practical multi-model systems.

Finally, related work also comes from multi-model databases, polyglot persistence, and query federation. Existing systems often provide a common access layer over heterogeneous sources or extend one dominant query language to cover additional models. A broad overview of this landscape is given in~\citep{Jiaheng2023Survey}. On the standards side, \acrshort{sql} has been extended toward particular combinations of models, for example by SQL/XML~\citep{SQLXML}, SQL/JSON~\citep{SQLJSON}, and SQL/PGQ~\citep{SQLPGQ}. These standards are important, but each covers only a subset of the multi-model problem. Similarly, polystore and mediator-style systems~\citep{conf/cikm/LuHC18, DBLP:journals/ijcc/BondiombouyV16,alotaibi2020estocada} show how queries can be executed across heterogeneous backends, yet they usually treat local representations as given rather than deriving them from an explicit conceptual schema and its mappings. In contrast, our framework combines conceptual modeling, logical representation, mappings, and querying in one coherent foundation.
