\section{Complementary Approaches to Multi-Model Data Management}
\label{sec:related-concepts}
\defineQuestionPrefix{be}{B}
\defineQuestionPrefix{sf}{S}

This section collects two complementary lines of work that support the practical side of the thesis. The first concerns evaluation---if our modeling, querying, and self-adaptation techniques are to be useful, we need datasets and workloads that are both realistic and sufficiently diverse. The second concerns a more lightweight approach to cross-model querying. While the main line of the thesis is based on explicit schemas and mappings, we also wanted to explore a more pragmatic route focused on rapid interoperability over already existing heterogeneous data.

\subsection{Benchmarking \& Evaluation}

A novel approach can be interesting and theoretically sound; however, to be useful in practice, it must be evaluated on realistic datasets and workloads. In the context of multi-model data management, this is particularly challenging, as there are only a few real-world multi-model datasets and queries.

\subsubsection{Related Work}

Most established benchmarks are single-model. Classical representatives such as TPC-H~\citep{tpch} and TPC-DS~\citep{tpcds} target relational workloads, XMark~\citep{10.5555/1287369.1287455} and DeepBench~\citep{10.1145/3531348.3532176} focus on hierarchical or document-style data, and graph-specific benchmarking is covered by suites such as LDBC-SNB~\citep{10.1145/2723372.2742786} or by surveys of graph generators~\citep{10.1145/3379445}.

Only a few benchmarks explicitly target multi-model systems. BigBench~\citep{10.1145/2463676.2463712} combines relational, semi-structured, and unstructured data; UniBench~\citep{unibench} focuses on a multi-model workload within a single integrated scenario; and M2Bench~\citep{10.14778/3574245.3574259} broadens the supported model combinations for analytical workloads. These tools are valuable, but they do not directly address all the possible combinations of multiple models, embeddings, and cross-model query plans that matter in our setting.

Also, the presented datasets consist of only a few kinds (${\sim} 10$) and a small number of relatively simple queries (10--30). This makes it difficult to evaluate the approaches proposed in the previous sections---the state space of possible configurations for self-adaptation grows exponentially with the number of kinds, so we need to benchmark them on realistic schemas with substantially more kinds and structural variation than current multi-model benchmarks provide. Similarly, the query-optimization algorithms require complex cross-model queries to test both their effectiveness and efficiency. Moreover, each of these benchmarks provides only a single version of both the schema and the queries, which is not sufficient for evaluating evolution management.

\subsubsection{Research Challenges}

Existing practice usually falls back to two imperfect strategies. The first is to generate a synthetic dataset, which is often not realistic enough and takes a lot of time to design and implement. The second is to start from an existing dataset and transform it into the required representation. This means writing a new custom transformation script for each dataset and target scenario. Such scripts are difficult to reuse, hard to validate semantically, and often too ad hoc to support reproducible benchmarking across many model combinations. Based on these limitations, we identified the following research challenges:

\question{be}{benchmark-coverage}{Benchmark coverage}{Evaluation of multi-model systems should cover a diverse set of relevant combinations of data models, embeddings, and redundancy patterns. For instance, the approaches discussed in this thesis require evaluation across many alternative logical representations of the same data on the conceptual level, often at much larger schema scales and with more complex cross-model interactions than current multi-model benchmarks provide.}

\question{be}{evolution-variants}{Evolution variants}{When testing evolution management, we need to evaluate the system's ability to propagate changes of the conceptual schema. The benchmark should therefore provide multiple variants of the same dataset, each corresponding to a different change on the conceptual level.}

\question{be}{reusable-derivation}{Reusable derivation}{The system should be able to derive multi-model datasets from existing data in a universal and repeatable way. We needed a representation-independent process that preserves the meaning of the original data, records the applied transformations, and systematically generates multiple multi-model variants.}

\question{be}{benchmarking-queries}{Benchmarking queries}{A useful benchmark consists not only of data, but also of queries that stress the intended capabilities of the evaluated system. In the multi-model setting, these workloads should remain comparable across alternative representations and across evolution steps, including cases where only the logical mapping changes and cases where the conceptual schema itself evolves.}

\subsubsection{TransforMMer}

The main idea behind our approach, proposed in \paperRef{enase_2025} (and further developed in~\citep{is_2026} (under review)), is to use the categorical framework described in previous sections to automate the transformation of a given dataset into a multi-model representation.

Not all data models are schema-full, so the first step is to infer the schema of the input dataset. For that, we use an existing approach proposed by our research group~\citep{mm_infer, koupil2022mminfer}. Unlike most of our previous work, it is not based on category theory, so we adapted it to the categorical framework. It can infer both conceptual and logical schemas (represented by schema categories), as well as the mappings between them.

The next step requires limited manual refinement,
%not because the inference is unreliable, but 
because some semantic decisions cannot be recovered from the data alone. For example, the inference algorithm can identify candidates for references and identifiers, but it cannot always determine which of them are actually intended by the users or the application logic. Therefore, users confirm the correct ones and add any semantically missing identifiers or references. Another common task is the unification of structurally similar schema fragments---e.g., if a document contains multiple nested subdocuments under different keys, the inference algorithm will naturally treat them as separate kinds even when they are semantically the same.

Crucially, at this stage we allow only changes that are performed via \emph{light} operations (see \Cref{sec:evolution-propagation}). This way, we can easily update the previously inferred mappings to make them consistent with both the refined conceptual schema and the original logical schema, so we can use them to import the data into the instance category corresponding to the refined conceptual schema.

Finally, users can choose the desired logical representation of the data, and the system will automatically transform the instance category into that representation. Users can also choose multiple different representations, or change them over time as workloads or design goals shift. This is a major advantage of our approach---it allows us to present a single dataset in many combinations of data models while preserving semantic equivalence to the original data, and it also enables us to simulate migrations from one logical configuration to another.

\begin{example}
\label{ex:transformmer-sc}
Let us start with an already existing dataset. Again, we will use the Yelp data in multi-model format (as shown in \Cref{fig:mm-data}), although the initial representation can be arbitrary. The first part of \Cref{fig:transformmer-sc} shows the inferred conceptual schema, consisting of several disconnected components. The three-dot symbol is used as an abbreviation for properties that are not relevant to the example.

The system can automatically identify reference candidates; in this case, \object{user\_id} refers to \object{id}, and \object{business\_id} refers to \object{\_id}. Users can then refine the schema by confirming the reference candidates. This operation can be represented via a functor between the old and the new schema, mapping morphism \signature{2} to \signature{6.1} and morphism \signature{3} to \signature{7.4}. Note that some objects were renamed; this is only a cosmetic change that users can make to improve consistency and readability.

The final conceptual schema can be mapped to any number of logical representations. Let us focus only on the \object{Business}-\object{Attributes} part. Users have chosen to map it to a relational representation with two tables, another relational representation with one table (and all properties of \object{Attributes} embedded as columns), and a document representation with one collection and a nested subdocument for \object{Attributes}. The system will then transform the data into all three representations.
\end{example}

This approach is not limited to various logical representations of the same conceptual schema---we can also leverage the evolution-management techniques described in \Cref{sec:evolution-propagation} to simulate evolution of the conceptual schema. Users can apply any of the \acrshort{smo}s to generate multiple different versions of the conceptual schema. The system will take care of propagating the changes to the logical schemas and to the data, so that all representations remain semantically aligned with each other and with the original data.

Queries are generated in a similar way. First, users employ \acrshort{mmql} to define a set of queries over the conceptual schema, which are then evolved together with the schema. Finally, we use the \acrshort{mmql} query engine to generate query plans, which transform the queries into the chosen logical representation without executing them. This gives us comparable workload variants not only across different logical representations, but also across successive conceptual versions of the benchmark.

A proof-of-concept implementation of this approach is described in \paperRef{edbt_2025}. We used it in~\citep{is_2026} to compare the performance of different logical representations in several multi-model scenarios, including evolution of the conceptual schema.

\subsection{Schema-free Query Unification}

This problem is motivated by highly dynamic settings---such as data lakes, browser-side data integration, or loosely coupled collections of services---where heterogeneous data already exists in multiple forms and users need to query it quickly, often without first constructing a stable conceptual schema and explicit mappings~\citep{CSUR-Jiaheng,AWSDataLake}. In such environments, the main obstacle is not only the coexistence of multiple data models, but also the coexistence of multiple query languages and execution paradigms.

\subsubsection{Related Work}

Existing approaches to multi-model querying usually follow one of two broad strategies. Polystores tend to expose a unified access layer over heterogeneous back-end systems, but often keep model-specific languages and execution engines underneath. Multi-model databases, on the other hand, commonly extend one dominant language, usually \acrshort{sql}, with constructs for additional models~\citep{Jiaheng2023Survey}. This includes standards and systems such as SQL/XML~\citep{SQLXML}, SQL/JSON~\citep{SQLJSON}, SQL/PGQ~\citep{SQLPGQ}, Myria~\citep{conf/cidr/WangBBHHHHJMMMM17}, Apache Drill~\citep{Hausenblas2013ApacheDI}, or CloudMdsQL~\citep{Kolev2016TheCM}. All of these are important steps toward practical interoperability, but they usually retain one privileged top-level language and support only limited forms of embedding.

There are also systems that relax this restriction only partially. Apache AGE~\citep{web:apacheage,github:apacheage}, for example, embeds Cypher into PostgreSQL through the \texttt{cypher()} function, but only in the Cypher-to-SQL direction. Systems such as OrientDB~\citep{orientdb} or ArangoDB~\citep{arangodb} support several models as well, yet they do so mainly through proprietary syntax or a system-defined language. BigDAWG~\citep{journals/sigmod/DugganESBHKMMMZ15} comes closer to language plurality by allowing different query islands, but it still separates them into predefined access modes rather than supporting unrestricted recursive combinations inside one query.

\subsubsection{Research Challenges}

Our goal was not to define yet another universal user language, but to preserve existing ones and connect them through a shared algebraic layer. We identified the following research challenges:

\question{sf}{language-interoperability}{Language interoperability}{Different query languages are designed for different data models and therefore have different operators, semantics, and execution paradigms. In a heterogeneous environment, the system should allow users to combine established query languages without limitations on the top-level language, or on the nesting depth or direction.}

\question{sf}{unified-algebra}{Unified algebra}{If multiple query languages are to interoperate in a principled way, they need a shared internal representation that captures their essential operators. Such a representation must be expressive enough to serve as a common compilation target, but also simple enough to support systematic reasoning and execution. The challenge is to design a unified algebra that preserves the core semantics of these operators while enabling mixed queries to be analyzed as a single plan.}

\question{sf}{schema-free}{Schema-free querying}{In a highly dynamic environment, the system should be able to query the data even when no stable schema and no explicit mappings have been prepared in advance. Instead, it should recover the structure from the query and the accessed data fragments to make the mixed query meaningful and executable.}

\subsubsection{DortDB}

In \paperRef{vldb_2025_dortdb}, we addressed these problems with a novel approach called \term{DortDB}. Rather than introducing yet another user-facing universal language, it treats interoperability itself as the main goal: \acrshort{sql}~\citep{SQL}, XQuery~\citep{XQuery}, and Cypher~\citep{Cypher} can be nested into one another recursively, and the mixed query is then translated into a \emph{unified algebra}~\citep{jezek_2026} (under review) covering relational, hierarchical, and graph-style operations~\citep{DBLP:conf/icde/ReSF06,DBLP:conf/edbt/AnglesBGV25,DBLP:conf/sigmod/HolschGS16}. This allows mixed-language cross-model queries to be formulated without committing to a single privileged language, as illustrated later in \Cref{ex:dortdb-rewrite}. It also keeps the setup lightweight---rather than requiring a stable shared schema in advance, DortDB derives the necessary local structure from the query and the accessed data fragments.

The unified algebra is the key contribution of this approach. Internally, it acts as a common compilation target over a schema-agnostic object representation of the data. It integrates tuple-oriented operators known from relational algebra, operators for item-oriented and hierarchical processing inspired by XQuery, and path-oriented operators needed for graph traversal. As a result, nested fragments written in different languages are no longer treated as opaque foreign calls; instead, they become parts of one logical plan tree whose operators can be inspected, rearranged, simplified, and executed uniformly, even though the system starts without an explicit conceptual schema.

\begin{example}
\label{ex:dortdb-rewrite}
The query from \Cref{ex:querying-multi} uses SQL for both the \object{User} and the \object{Review} data. However, the DortDB query engine allows us to express the same query in multiple different ways. E.g., we can express the main query in \acrshort{sql}, while the \object{Review} data is obtained from a nested XQuery subquery:
\begin{alltt}\small\ttfamily
\sql{SELECT} r.stars, user.name
\sql{FROM} user
\sql{JOIN} (
    \keyword{LANG xquery}
    \xquery{for} $review \xquery{in} $reviews/Review
    \xquery{where} $review/business_id = 'bus#679' \xquery{and} $review/stars \xquery{ge} 3
    \xquery{return} $review
) r \sql{ON} r.user_id = user.id
\sql{ORDER BY} r.stars \sql{ASC}
\end{alltt}
Alternatively, we can use Cypher in the main query for \object{Review}, while the \object{User} data is obtained from a nested SQL subquery:
\begin{alltt}\small\ttfamily
\cypher{MATCH} (review:Review)
\cypher{WHERE} review.business_id = 'bus#679' \cypher{AND} review.stars >= 3
\cypher{UNWIND} (
    \keyword{LANG sql}
    \sql{SELECT} user.id, user.name
    \sql{FROM} user
    \sql{WHERE} user.id = review.user_id
) \cypher{AS} u
\cypher{RETURN} review.stars \cypher{AS} stars, u.name \cypher{AS} name
\cypher{ORDER BY} stars \cypher{ASC}
\end{alltt}

Note the \texttt{\keyword{LANG}} keyword, which allows us to switch between languages at any point in the query. In practice, the choice of which language to use for which part of the query can be guided by users' familiarity with the languages, the expected performance of the underlying engines, or other practical considerations. The DortDB query engine will then translate the entire query into the unified algebra and optimize it as a whole. The final plans are displayed in \Cref{fig:dortdb-algebra}.
\end{example}

DortDB should not be seen as a replacement for the categorical framework, but rather as a complementary point in the design space. Our main line of work starts from an explicit conceptual schema, derives logical schemas and mappings, and uses this structure to support querying, evolution, and eventually self-adaptation. DortDB starts much lower and more pragmatically---it assumes heterogeneous data is already present, keeps the representation intentionally schema-free, and focuses on making cross-model querying workable with minimal upfront setup. The price is that it does not provide the same semantic guarantees, principled evolution machinery, or explicit reasoning about equivalence between alternative representations. The benefit is speed of adoption and flexibility in dynamic or exploratory settings.

This makes DortDB especially relevant in scenarios where a fully modeled solution would be too costly or too premature. It can be understood as a universal mediator layer for rapid integration of existing sources, prototyping of cross-model workloads, or interactive analysis over data whose structure is still evolving. At the same time, it broadens the thesis by exploring a more pragmatic branch of multi-model querying, focused on language interoperability rather than on explicit shared semantics. Once the data and workloads stabilize, the schema-first categorical approach offers stronger guarantees and deeper automation. Conversely, DortDB shows that there is practical value in supporting heterogeneous querying even before such a full semantic model is available.

These ideas were also validated, as well as evaluated in terms of performance~\citep{jezek_2026}, in a proof-of-concept prototype. For now, the system is intentionally in-memory and read-only, allowing us to focus on core interoperability and optimization problems without being distracted by storage or transaction management. However, it already supports the whole unified algebra, thus covering a large portion of the most commonly used operators from \acrshort{sql}, XQuery, and Cypher.

\subsection{Contributions}

\contribution{Benchmark Derivation}
TransforMMer contributes a transformation-driven approach to benchmark engineering for heterogeneous information systems (\paperRef{enase_2025}). Instead of treating a benchmark as one fixed dataset, it derives families of semantically aligned multi-model variants from existing data (\questionRef{be}{benchmark-coverage}). The categorical basis ensures reusable derivation in a controlled, repeatable way (\questionRef{be}{reusable-derivation}).

\contribution{Benchmark Evolution}
The same framework also supports benchmark evolution as a first-class concern. By versioning both conceptual and logical variants and by evolving queries together with the schema, it makes it possible to evaluate propagation scenarios (\questionRef{be}{evolution-variants}) and benchmark queries (\questionRef{be}{benchmarking-queries})~\citep{is_2026}.

\contribution{Prototype Validation}
There is a proof-of-concept tool called TransforMMer, described in \paperRef{edbt_2025} and further evaluated in~\citep{is_2026}. Overall, this work is essential for evaluating the other two main contributions of the thesis---evolution management and self-adaptation---as it provides a systematic way to generate realistic multi-model datasets and workloads, including evolution scenarios.\\

\contribution{Language Interoperability}
DortDB contributes a lightweight alternative for situations where explicit shared semantics would be too costly or limiting. Its main idea is to preserve established query languages (for now \acrshort{sql}, XQuery, and Cypher) and allow them to interoperate symmetrically, so that they can be nested into one another without a privileged top-level language (\questionRef{sf}{language-interoperability}). It is enabled by a unified algebra~\citep{jezek_2026} that serves as a common compilation target for mixed queries (\questionRef{sf}{unified-algebra}), allowing for seamless integration and comprehensive optimization.

\contribution{Schema-free Querying}
At the same time, DortDB keeps the setup intentionally schema-free. The required local structure is derived from the query itself, enabling heterogeneous querying even in dynamic, loosely integrated settings (\questionRef{sf}{schema-free}). The approach, together with a proof-of-concept prototype, is presented in \paperRef{vldb_2025_dortdb}. Within the thesis, it complements the main schema-centric line by offering a practical alternative for specific use cases, and by exploring what can already be achieved at the query-processing level before a full semantic model is available.
