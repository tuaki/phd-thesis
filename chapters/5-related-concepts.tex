\section{Related Concepts}
\label{sec:related-concepts}

This section collects two complementary lines of work that support the practical side of the thesis. The first concerns evaluation---if our modeling, querying, and self-adaptation techniques are to be useful, we need datasets and workloads that are both realistic and sufficiently diverse. The second concerns a more lightweight approach to cross-model querying. While the main line of the thesis is based on explicit schemas and mappings, we also wanted to explore a more pragmatic route focused on rapid interoperability over already existing heterogeneous data.

\subsection{Benchmarking \& Evaluation}

A novel approach can be interesting and theoretically sound, however, in order to be useful in practice, it must be evaluated on realistic datasets and workloads. In the context of multi-model data management, this is particularly challenging, as there is a lack of real-world multi-model datasets and queries. First of all, most available datasets are single-model, specifically relational. The few existing multi-model benchmarks (see \Cref{sec:benchmarking-related-work}) cover only fixed combinations of models, even though there are many possible combinations of models, embeddings, and other features we need to test.

Next, the current datasets (discussed in \Cref{sec:benchmarking-related-work}) usually use only a few kinds (${\sim} 10$) and define a small number of relatively simple queries (10--30). This makes it difficult to evaluate approaches proposed in the previous sections---the state space of possible configurations for self-adaptation grows exponentially with the number of kinds, so we need to benchmark it on realistic schemas, which can easily have hundreds of kinds. Similarly, the query optimization algorithms require complex cross-model queries to test both their effectivity and efficiency.

Existing practice usually falls back to two imperfect strategies. The first is to generate a synthetic dataset, which is often not realistic enough and takes a lot of time to design and implement. The second is to start from an existing single-model dataset and transform it into a multi-model representation. This usually means writing a new custom transformation script for each dataset and target scenario. Such scripts are difficult to reuse, hard to validate semantically, and often too ad hoc to support reproducible benchmarking across many model combinations.

Based on these observations, we identify the following open problems:

\question{be}{benchmark-coverage}{Benchmark coverage}{Evaluation of multi-model systems should cover realistic combinations of data-models, embeddings, and redundancy patterns. For instance, the approaches discussed in this thesis require evaluation across many alternative logical representations of the conceptually same data, often at much larger schema scales and with more complex cross-model interactions than current multi-model benchmarks provide.}

\question{be}{evolution-variants}{Evolution variants}{When testing evolution management, we need to evaluate the system's ability to propagate changes of the conceptual schema. The benchmark should therefore provide multiple variants of the same dataset, each correspoding to a different change on the conceptual level.}

\question{be}{reusable-derivation}{Reusable derivation}{The system should be able to derive multi-model datasets from existing data in a universal and repeatable way. We needed a representation-independent process that preserves the meaning of the original data, records the applied transformations, and systematically generates multiple multi-model variants.}

\question{be}{benchmarking-queries}{Benchmarking queries}{A useful benchmark consists not only of data, but also of queries that stress the intended capabilities of the evaluated system. In the multi-model setting, these workloads should remain comparable across alternative representations and across evolution steps, including cases where only the logical mapping changes and cases where the conceptual schema itself evolves.}

The main idea behind our approach is to use the categorical framework, described in previous sections, to automate the transformation of a given dataset into a multi-model representation.

Because not all data models are schema-full, the first step is to infer the schema of the input dataset. For that, we use an existing approach~\citep{mm_infer, koupil2022mminfer}. Unlike most of our previous work, it is not based on category theory, so we adapted it to the categorical framework. It is capable of inferring both conceptual and logical schemas (represented by schema categories), as well as the mappings between them.

The next step requires limited manual refinement, not because the inference is unreliable, but because some semantic decisions cannot be recovered from the data alone. For example, the inference algorithm can identify candidates for references and identifiers, but it cannot always determine which of them are actually intended by the users or the application logic. Therefore, the users confirm the correct ones and add any semantically missing identifiers or references. Another common task is unification of structurally similar schema fragments---e.g., if a document contains multiple nested subdocuments under different keys, the inference algorithm will naturally treat them as separate kinds even when they are semantically the same. This can then be resolved explicitly with operations such as \code{asMap} from \Cref{ex:evolution-map}.

In fact, all changes to the conceptual schema are represented as \acrshort{smo}s, which allow seamless propagation to the logical schemas. Crucially, we only allow changes that keep the logical schemas consistent with the original data. This way, we can always import it to the instance category corresponding to the refined conceptual schema. This also lets us model benchmark evolution explicitly---once the conceptual schema is refined, we can propagate the change to all target representations and compare successive benchmark versions under controlled conditions.

Finally, the users can choose the desired logical representation of the data, and the system will automatically transform it from the instance category to the chosen representation. The users can also choose multiple different representations, or change them over time as workloads or design goals shift. This is a major advantage of our approach---it allows us to present a single dataset in many combinations of data models while keeping semantic equivalence to the original data, and it also makes it possible to simulate migrations from one logical configuration to another.

Queries are generated in a similar way. First, the users use \acrshort{mmql} to define a set of queries over the conceptual schema, which are then evolved together with the schema. Finally, we use the \acrshort{mmql} query engine to generate query plans, which transforms the queries to the chosen logical representation without executing them. This gives us comparable workload variants not only across different representations, but also across successive conceptual and logical versions of the benchmark.

An in-depth description of the approach can be found in \paperRef{enase_2025}. There is also a proof-of-concept implementation called \term{TransforMMer}, available in \paperRef{edbt_2025}.

\subsubsection{Related Work}
\label{sec:benchmarking-related-work}

Existing evaluation practice usually follows two paths---fixed benchmarks and synthetic generators. Most established benchmarks are still single-model. Classical representatives such as TPC-H~\citep{tpch} and TPC-DS~\citep{tpcds} target relational workloads, XMark~\citep{10.5555/1287369.1287455} and DeepBench~\citep{10.1145/3531348.3532176} focus on hierarchical or document-style data, and graph-specific benchmarking is covered by suites such as LDBC-SNB~\citep{10.1145/2723372.2742786} or by surveys of graph generators~\citep{10.1145/3379445}. These tools are valuable, but they do not directly address the combination of multiple models, embeddings, and cross-model query plans that matters in our setting.

Only a few benchmarks target multi-model systems explicitly. BigBench~\citep{10.1145/2463676.2463712} combines relational, semi-structured, and unstructured data, UniBench~\citep{unibench} focuses on a multi-model workload over one integrated scenario, and M2Bench~\citep{10.14778/3574245.3574259} broadens the supported model combinations for analytical workloads. Even so, these benchmarks still fix the benchmark scenarios in advance. Our goal is different---rather than defining one more fixed workload, we want to generate semantically equivalent multi-model representations and related queries from an input dataset, so that the evaluation can be adapted to the particular questions raised by our framework.

\subsection{Schema-free Query Unification}

\defineQuestionPrefix{sf}{S}

This problem is motivated by highly dynamic settings---such as data lakes, browser-side data integration, or loosely coupled collections of services---where heterogeneous data already exists in multiple forms and users need to query it quickly, often without first constructing a stable conceptual schema and explicit mappings~\citep{CSUR-Jiaheng,AWSDataLake}. In such environments, the main obstacle is not only the coexistence of multiple data models, but also the coexistence of multiple query languages and execution paradigms. Existing systems often force users either to adopt one dominant top-level language (with one-directional extensions) or to connect several language fragments by ad hoc glue code~\citep{Jiaheng2023Survey,journals/sigmod/DugganESBHKMMMZ15,Kolev2016TheCM}.
Based on these observations, we identify the following open problems:

\question{sf}{language-interoperability}{Language interoperability}{Different query languages are designed for different data models and therefore have different operators, semantics, and execution paradigms. In a heterogeneous environment, the system should allow users to combine established query languages without limitations on the top-level language, or on the nesting depth or direction.}

\question{sf}{unified-algebra}{Unified algebra}{If multiple query languages are to interoperate in a principled way, they need a shared internal representation that captures their essential operators. Such a representation must be expressive enough to serve as a common compilation target, but also simple enough to support systematic reasoning and execution. The challenge is to design a unified algebra that preserves the core semantics of these languages while making mixed queries analyzable as one plan.}

\question{sf}{schema-free}{Schema-free querying}{In a highly dynamic environment, the system should be able to query the data even when no stable schema and no explicit mappings have been prepared in advance. Instead, it should recover the structure from the query and the accessed data fragments to make the mixed query meaningful and executable.}

In \paperRef{vldb_2025_dortdb}, we addressed these problems with a novel approach called \term{DortDB}. Rather than introducing yet another user-facing universal language, it treats interoperability itself as the main goal: \acrshort{sql}~\citep{SQL}, XQuery~\citep{XQuery}, and Cypher~\citep{Cypher} can be nested into one another recursively, and the mixed query is then translated into a unified algebra covering relational, hierarchical, and graph-style operations~\citep{DBLP:conf/icde/ReSF06,DBLP:conf/edbt/AnglesBGV25,DBLP:conf/sigmod/HolschGS16}. This makes it possible to formulate genuinely cross-model queries without committing to one privileged language, as illustrated later in \Cref{ex:dortdb-rewrite}. It also keeps the setup lightweight---rather than requiring a stable shared schema in advance, DortDB derives the needed local structure from the query and the accessed data fragments.

The unified algebra is the key contribution of this approach. Internally, it acts as a common compilation target over a schema-agnostic object representation of the data. It integrates tuple-oriented operators known from relational algebra, operators for item-oriented and hierarchical processing inspired by XQuery, and path-oriented operators needed for graph traversal. As a result, nested fragments written in different languages are no longer treated as opaque foreign calls; instead, they become parts of one logical plan tree whose operators can be inspected, rearranged, simplified, and executed uniformly, even though the system started without an explicit conceptual schema.

Once the query is represented in this form, optimization can be performed in a model-independent way, for example, by operator reordering, elimination of redundant nested evaluations, expression simplification, and index-aware rewriting~\citep{DBLP:conf/sigmod/HolschGS16}. In this sense, DortDB is a contribution on its own; it demonstrates that language-level unification of heterogeneous querying is feasible, practically useful, and not limited to shallow embeddings. These ideas were also validated in a proof-of-concept prototype.

DortDB should not be seen as a replacement for the categorical framework, but rather as a complementary point in the design space. Our main line of work starts from an explicit conceptual schema, derives logical schemas and mappings, and uses this structure to support querying, evolution, and eventually self-adaptation. DortDB starts much lower and more pragmatically---it assumes heterogeneous data is already present, keeps the representation intentionally schema-free, and focuses on making cross-model querying workable with minimal upfront setup. The price is that it does not provide the same semantic guarantees, principled evolution machinery, or explicit reasoning about equivalence between alternative representations. The benefit is speed of adoption and flexibility in dynamic or exploratory settings.

This makes DortDB especially relevant in scenarios where a fully modeled solution would be too costly or too premature. It can be understood as a universal mediator layer for rapid integration of existing sources, prototyping of cross-model workloads, or interactive analysis over data whose structure is still evolving. At the same time, it also broadens the thesis by exploring a more pragmatic branch of multi-model querying, focused on language interoperability rather than on explicit shared semantics. Once the data and workloads stabilize, the schema-first MM-cat approach offers stronger guarantees and deeper automation. Conversely, DortDB shows that there is practical value in supporting heterogeneous querying even before such a full semantic model is available. Its current prototype nature must, however, be kept in mind: the system is intentionally in-memory, read-only, and primarily rule-based in its optimization, so it should be viewed as a lightweight interoperability mechanism, intended for specific use cases, rather than a full replacement for more deeply modeled or more mature database solutions.

\begin{example}
\label{ex:dortdb-rewrite}
The query from \Cref{ex:querying-multi} uses SQL for both the \object{User} and \object{Review} data. However, the DortDB query engine allows us to express the same query in multiple different ways. E.g., we can express the main query in \acrshort{sql}, while the \object{Review} data is obtained from a nested XQuery subquery:
\begin{alltt}\small\ttfamily
\sql{SELECT} r.stars, user.name
\sql{FROM} user
\sql{JOIN} (
    \keyword{LANG xquery}
    \xquery{for} $review \xquery{in} $reviews/Review
    \xquery{where} $review/business_id = 'bus#679' \xquery{and} $review/stars >= 3
    \xquery{return} \{
        "user_id": $review/user_id,
        "stars": $review/stars
    \}
) r \sql{ON} r.user_id = user.id
\sql{ORDER BY} r.stars \sql{ASC}
\end{alltt}
Or, we can use Cypher in the main query for the \object{Review}, while the \object{User} data is obtained from a nested SQL subquery:
\begin{alltt}\small\ttfamily
\cypher{MATCH} (review:Review)
\cypher{WHERE} review.business_id = 'bus#679' \cypher{AND} review.stars >= 3
\cypher{UNWIND} (
    \keyword{LANG sql}
    \sql{SELECT} user.id, user.name
    \sql{FROM} user
    \sql{WHERE} user.id = review.user_id
) \cypher{AS} u
\cypher{RETURN} review.stars \cypher{AS} stars, u.name \cypher{AS} name
\cypher{ORDER} \cypher{BY} stars \cypher{ASC}
\end{alltt}

Note the \texttt{\keyword{LANG}} keyword which allows us to switch between languages at any point in the query. In practice, the choice of which language to use for which part of the query can be guided by the users' familiarity with the languages, the expected performance of the underlying engines, or other practical considerations. The DortDB query engine will then translate the entire query into the unified algebra and optimize it as a whole.
\end{example}

\subsubsection{Related Work}

Existing approaches to multi-model querying usually follow one of two broad strategies. Polystores tend to expose a unified access layer over heterogeneous back-end systems, but often keep model-specific languages and execution engines underneath. Multi-model databases, on the other hand, commonly extend one dominant language, usually \acrshort{sql}, with constructs for additional models~\citep{Jiaheng2023Survey}. This includes standards and systems such as SQL/XML~\citep{SQLXML}, SQL/JSON~\citep{SQLJSON}, SQL/PGQ~\citep{SQLPGQ}, Myria~\citep{conf/cidr/WangBBHHHHJMMMM17}, Apache Drill~\citep{Hausenblas2013ApacheDI}, or CloudMdsQL~\citep{Kolev2016TheCM}. All of these are important steps toward practical interoperability, but they usually retain one privileged top-level language and support only limited forms of embedding.

There are also systems that relax this restriction only partially. Apache AGE~\citep{web:apacheage,github:apacheage}, for example, embeds Cypher into PostgreSQL through the \texttt{cypher()} function, but only in the Cypher-to-SQL direction. Systems such as OrientDB~\citep{orientdb} or ArangoDB~\citep{arangodb} support several models as well, yet they do so mainly through proprietary syntax or a system-defined language. BigDAWG~\citep{journals/sigmod/DugganESBHKMMMZ15} comes closer to language plurality by allowing different query islands, but it still separates them into predefined access modes rather than supporting unrestricted recursive combinations inside one query.

Against this background, DortDB contributes a more symmetric form of language interoperability. Its goal is not to define yet another universal user language, but to preserve existing ones and connect them through a shared algebraic layer. This is precisely where it differs from the main line of this thesis. The categorical framework aims at explicit shared semantics across models, whereas DortDB aims at practical interoperability across languages over already existing heterogeneous data.

\subsection{Contributions}

This chapter contributes two complementary perspectives that support the rest of the thesis from outside its main schema-centric core.

The first perspective concerns evaluation. We formulated benchmarking itself as a multi-model problem: if the proposed methods are to be tested seriously, we need datasets and workloads that can cover many combinations of models, embeddings, redundancies, query patterns, and evolution scenarios rather than one fixed benchmark scenario. \term{TransforMMer} addresses this by using schema inference, conceptual refinement, semantics-preserving transformations, and \acrshort{mmql}-based query derivation to generate multiple related multi-model representations and workloads from a common input dataset. Because these variants can also be versioned at both the conceptual and logical levels, the framework can simulate redesign and migration scenarios instead of benchmarking only one static configuration. In this sense, its contribution is not just another benchmark, but a general mechanism for deriving benchmarks that are adaptable to the specific questions raised by our framework.

The second perspective concerns the limits of explicit semantic modeling. While the main line of the thesis assumes a conceptual schema and explicit mappings, DortDB shows that some practical situations call for a lighter solution that starts directly from already existing heterogeneous data and query languages. Its main contribution is a unified algebraic backbone that makes recursive combinations of established languages executable and optimizable as one mixed query, while deriving the needed local structure on demand instead of requiring a full shared schema in advance. This places DortDB not in opposition to the rest of the thesis, but at a different point in the design space: MM-cat emphasizes explicit shared semantics and long-term manageability, whereas DortDB emphasizes rapid interoperability and exploratory cross-model querying.

Taken together, these results broaden the scope of the thesis in two directions. TransforMMer strengthens the empirical basis of the proposed framework by making systematic evaluation more realistic and reproducible. DortDB, in turn, shows that the broader multi-model agenda also includes cases where interoperability must be achieved before a full conceptual model is available. Both contributions therefore complement the central research line while also clarifying its practical context and boundaries.
